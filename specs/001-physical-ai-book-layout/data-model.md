# Data Model Overview

This document outlines the conceptual data models relevant to the "Physical AI & Humanoid Robotics" book. While the book primarily focuses on instructional content rather than a software application with a persistent database, understanding the structure of information—especially concerning robot states, sensor data, and inter-component communication—is crucial for effective learning and implementation in robotics.

## 1. Robot State Representation

### 1.1. Joint State

-   **Description**: Represents the current configuration of a robot's joints.
-   **Fields**:
    -   `names`: (Array of strings) Names of the joints.
    -   `positions`: (Array of floats) Angular or linear position of each joint.
    -   `velocities`: (Array of floats) Velocity of each joint.
    -   `efforts`: (Array of floats) Force/torque applied at each joint.
-   **Context**: Often used in URDF (Unified Robot Description Format) for static models and dynamic simulations (e.g., in Gazebo) via ROS 2 `sensor_msgs/JointState` messages.

### 1.2. Pose and Transform

-   **Description**: Represents the position and orientation of a robot link or object in 3D space.
-   **Fields**:
    -   `position`: (x, y, z - floats) Cartesian coordinates.
    -   `orientation`: (x, y, z, w - floats) Quaternion representation for rotation.
-   **Context**: Fundamental for navigation, manipulation, and visualization. Used in ROS 2 `geometry_msgs/Pose` and `geometry_msgs/TransformStamped` messages, and the TF (Transform) tree.

## 2. Sensor Data Models

### 2.1. Image Data

-   **Description**: Raw or processed image data from cameras.
-   **Fields**:
    -   `header`: (Timestamp, frame_id) Metadata about the image capture.
    -   `height`, `width`: (Integers) Dimensions of the image.
    -   `encoding`: (String) Encoding of the pixels (e.g., `rgb8`, `mono16`).
    -   `is_bigendian`: (Integer) Byte order.
    -   `step`: (Integer) Full row length in bytes.
    -   `data`: (Array of bytes) The raw image data.
-   **Context**: Used for computer vision tasks (perception, object detection) with ROS 2 `sensor_msgs/Image` messages and often processed by libraries like OpenCV.

### 2.2. Point Cloud Data

-   **Description**: A set of data points in 3D space, typically from LiDAR or depth cameras.
-   **Fields**:
    -   `header`: (Timestamp, frame_id).
    -   `height`, `width`: (Integers) Dimensions (for organized clouds).
    -   `fields`: (Array of `PointField`) Describes channels (e.g., x, y, z, rgb).
    -   `is_dense`: (Boolean) True if there are no invalid points.
    -   `data`: (Array of bytes) The raw point cloud data.
-   **Context**: Used for 3D mapping, object recognition, and navigation with ROS 2 `sensor_msgs/PointCloud2` messages.

### 2.3. IMU Data

-   **Description**: Data from an Inertial Measurement Unit (IMU), providing linear acceleration and angular velocity.
-   **Fields**:
    -   `header`: (Timestamp, frame_id).
    -   `orientation`: (Quaternion) Orientation estimation.
    -   `angular_velocity`: (Vector3) Angular velocity (rad/s).
    -   `linear_acceleration`: (Vector3) Linear acceleration (m/s^2).
-   **Context**: Essential for robot localization, balancing, and motion tracking with ROS 2 `sensor_msgs/Imu` messages.

## 3. Communication Models (ROS 2 Primitives)

### 3.1. Topics (Publisher/Subscriber)

-   **Description**: Asynchronous, one-to-many communication for streaming data.
-   **Example Data**: `sensor_msgs/JointState`, `geometry_msgs/Twist` (for velocity commands), `sensor_msgs/Image`.
-   **Conceptual Flow**: A node publishes messages on a topic; other nodes subscribe to receive them.

### 3.2. Services (Client/Server)

-   **Description**: Synchronous, request-response communication for discrete actions.
-   **Example Data**: Custom service messages for specific robot actions (e.g., `SetGripperPosition.srv`).
-   **Conceptual Flow**: A client sends a request; a server processes it and returns a response.

### 3.3. Actions (Client/Server with Feedback)

-   **Description**: Long-running, goal-oriented communication with periodic feedback and preemptability.
-   **Example Data**: `control_msgs/FollowJointTrajectory` (for complex motion planning).
-   **Conceptual Flow**: An action client sends a goal; an action server executes it, provides feedback, and eventually a result.

## 4. LLM Interaction Models

### 4.1. Task Planning Command

-   **Description**: Commands generated by an LLM for robot task execution.
-   **Fields**:
    -   `command_id`: (String) Unique ID for the command.
    -   `task_description`: (String) Natural language description of the task.
    -   `robot_actions`: (Array of Strings) Sequence of high-level robot actions (e.g., `move_to(x,y,z)`, `pick_object(id)`).
    -   `parameters`: (JSON/Dict) Associated parameters for actions.
-   **Context**: Used when integrating LLMs for high-level robot control and decision-making.
